# Explicit native alarm returning Light

`--foreground-alarm-sleep` extends the existing returning-Light selection only when `--alarm-client` and `--tagged-alarm-utilities` explicitly select the canonical API2 SDK. Legacy profiles and helper entrypoint remain unchanged. The deployment must provide the new `portable_app_foreground_idle_sleep_alarm` symbol and exact `alarm.service@2` instance; no implicit alarm grant, Points schedule, RTC control, SD or updater privilege is added.

The common adapter owns its existing service grant and a private copied ticket. Prepare runs bounded (64 phases), non-yielding fresh reconciliation after ordinary native preparation latency, validates descriptor/result/status and fresh matching snapshot/UTC, and refuses due/malformed plans. No service call intervenes after the accepted ticket. Duration zero means no schedule. Future deadlines use `(seconds - 1)*1000`, minimum1 ms and maximum24 hours, conservatively accounting for integer-second uncertainty. Early wake reconciles again; this is not precision alarm timing evidence.

The optional callback table is declared in `PortableForegroundIdle.h`: prepare/resume return1 ready/success,0 typed clean defer/refusal,-2 retained. Unknown results are terminal. The helper may resume exactly once only after successful Light and all power, panel, Runtime-token, key and temporary-grant restoration. Refusal never consumes a ticket. Adapter invalidates the ticket before resume dispatch and on every helper return; retained/unknown custody forbids further callbacks or cleanup. Wi-Fi retains its native service lease discipline; inability to obtain a post-wake resume lease retains instead of allowing an unreanchored service pump.

Existing eligibility, closed touch, native navigation, file safety, atomic/work guards and stack-preserving modal behavior remain. This profile does not enter Deep, save/discard drafts, unload apps or change the preference policy. GPIO and existing typed OTHER wake behavior remain deployment-owned; timed TIMER wake is additive.

Runtime273's sleep token parks native file/checkpoint access but does not itself block bound KV or realtime. The reviewed Badge NVS backend can service the six selected keys after ordinary panel/power preparation under actual provider-storage readiness and scoped resource leases. This is not authorization for arbitrary I/O, file-backed settings or Deep pad holds. Deployment helper tests must establish exact ordering and no-callback-after-retained behavior; app tests must preserve modal/draft state through timed and GPIO Light returns. Hardware remains unverified.
