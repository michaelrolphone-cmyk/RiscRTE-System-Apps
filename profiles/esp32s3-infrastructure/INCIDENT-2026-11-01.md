# ESP32 outage, 1 November 2026

The deployed relay identified itself as firmware 1.6.2. Its last health event
was at 07:13:26.342 UTC, after 85.19 minutes of uptime. It reported -55 dBm Wi-Fi,
7,713,079 bytes free heap, no queued deliveries, no consecutive network failures,
and no last error. Participant contact stopped at 07:14:18.119 UTC. The server
subsequently marked it stale/offline. These observations do not identify the
physical trigger. No serial session captured the failure and the installed
release has no OTA agent. Power, Wi-Fi, native execution failure and a service
response cannot be distinguished from the last heartbeat alone.

## Reproduced permanent-silence defect

In released source 13135a5a86b6b672ad47012dce62daf3d3b2b706, Node::received parses
response JSON before handling HTTP 5xx. A gateway's HTML/empty 502 response
therefore enters ProtocolBlocked. Node::advance refuses further work in that
phase, including the independent relay. The 1.6.2 supervisor deliberately feeds
the watchdog in responsive blocked states to avoid an earlier reboot loop.
Together these behaviors allow one transient service response to silence a
powered, running board indefinitely. The new regression fails on the released
source at the assertion that an HTML 502 must not enter ProtocolBlocked.
This is a demonstrated failure mechanism, not proof of this outage's trigger.

## 1.6.3 correction

- Classify HTTP 5xx, 408, 425 and 429 before parsing the response body.
- Retry unreadable responses and explicit service busy/rate-limit responses
  after 5, 10, 20, 40, then at most 60 seconds between attempts.
- Keep participant recovery separate from independently authenticated relay
  health and delivery. Relay success does not clear the participant failure.
- Preserve unresolved mutation requests exactly and reconcile their original
  operation identity before replay. Do not admit participant work during a hold.
- Keep true authentication/protocol rejections closed for participant work while
  continuing relay diagnostics. Storage corruption and retained cleanup still
  retain their original safety fences.
- Migrate the exact published 1.6.2 provider cohort to revision 13 without changing
  credentials, enrollment keys, subscriptions or pending custody.

The target build also uses the repository's ESP32-S3 compiler selector and
rejects non-little-endian ELF32 output. The generic unified Xtensa executable
must not silently select a different CPU configuration.

## Why earlier fixes were insufficient

Earlier releases addressed a hard five-second HTTP cap, missing provider
revisions and a blocked-state watchdog reboot loop. Separate physical devices
also shared an installation identity until their registration was corrected.
These were different failure modes. Eliminating resets did not provide recovery
from every application state; recovery responsibility moved into the state
machine without an independent health path in those states. Passing compilation
and normal-operation tests did not establish resilience under faults.

## Verification and remaining acceptance

The complete host suite passes, including prior recovery, captive portal,
terminal rejection, enrollment and relay tests. The new real state-machine test
injects gateway/body errors for two simulated hours, checks bounded retries,
continuing relay health, unchanged pending request bytes, receipt lookup,
auth/protocol isolation and storage fences. Simulated elapsed time is not
physical uptime. Package evidence records target compilation, sanitizer and
private-state migration results separately.

An enrolled board must use the preserving repair, never the unprovisioned full
initial image. First collect a private flash backup and redacted diagnostic
snapshot; retain the backup locally. Qualification remains open until the actual
board completes the scenarios in RECOVERY-QUALIFICATION.md and an uninterrupted
24-hour soak with no unexplained reset or health gap longer than two normal
three-minute heartbeat periods. Record recovery latency after service/AP
restoration and confirm catch-up and original operation identities. Extend the
observation to seven days before claiming a sustained uptime improvement.
